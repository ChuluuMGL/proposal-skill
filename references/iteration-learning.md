# Improve from actual proposal revisions

Use when the user asks to retain learning or update the skill. Do not silently publish skill changes after ordinary client work.

For each candidate lesson record:

| Observed problem | User correction / accepted result | Cause | Reusable decision | Where it applies | Regression example |
|---|---|---|---|---|---|

Classify before adding:
- **General decision:** unclear titles, unsupported recommendations, inconsistent scope → shared method/copy rules.
- **Format behavior:** sticky overlap, dialog focus, media-first black screen → web references and tested components.
- **Project configuration:** brand model, theme, service names, prices, logo spacing, server routes → remain in the client project.
- **Unresolved preference:** keep as hypothesis; do not label it an accepted standard.

Prefer updating or removing a conflicting old rule over adding another warning. Keep SKILL.md short; detailed examples belong in references/examples. Preserve working PPT capabilities when extending web output.

Use anonymized or synthetic examples. Do not publish client screenshots, identifying source paths, credentials, proprietary framework names, actual prices or unpublished commitments. A reusable component should accept replacement content and themes without carrying the original client's facts.

Before release:
1. Review the latest remote skill baseline; preserve improvements made elsewhere.
2. Route a few realistic requests: editable PPT, responsive HTML, narrow edit, audit-only. Check that format, scope, evidence and approval behavior match each request.
3. Validate metadata, links and runnable additions; inspect relevant viewport and interaction states. Preserve historical test limitations; do not claim a new whole-deck or real-device test from a component check.
4. Record version, changed behavior, tests, limitations and migration instructions where naming changes affect invocation.
5. On the next real proposal, compare recurring defect categories and revision causes. Aim to reduce avoidable rework, not promise one-shot approval or optimize for an arbitrary number of iterations.
